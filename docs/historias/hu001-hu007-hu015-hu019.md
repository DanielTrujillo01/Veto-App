# Integración HU-001, HU-007, HU-015 y HU-019

Las cuatro historias quedaron implementadas como módulos NestJS/TypeScript del monorepo `Veto-App`; las validaciones HTTP se comparten con `@veto/shared` y las escrituras usan `DatabaseService.withUser` y consultas parametrizadas.

## Rutas

| Método y ruta                                           | Contrato                                                                                                                                                                                                               |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/usuarios`                                    | Registra tutor; JSON `{nombre, celular, correo, password}` (también acepta `contrasena`); responde `201 {data}` sin hash.                                                                                              |
| `POST /api/aliados`                                     | Registra cuenta + aliado atómicamente; acepta los mismos campos y `nombreAliado?`, `tipo`, `descripcion?`, `contacto?`; responde `{data:{usuario,aliado}}`. Para veterinario independiente también crea `veterinario`. |
| `POST /api/aliados/:allyId/sedes`                       | Crea sede clínica; JSON `{nombre,direccion,ciudad}`. En local requiere `x-dev-ally-id` igual al parámetro de ruta.                                                                                                     |
| `GET /api/aliados/:allyId/sedes?incluirInactivas=true`  | Lista sedes activas por defecto; puede incluir desactivadas.                                                                                                                                                           |
| `PUT /api/aliados/:allyId/sedes/:branchId`              | Actualiza nombre, dirección y ciudad.                                                                                                                                                                                  |
| `PATCH /api/aliados/:allyId/sedes/:branchId/desactivar` | Desactivación lógica (`activa=false`).                                                                                                                                                                                 |
| `POST /api/aliados/:allyId/servicios`                   | Crea servicio con `{tipoServicioId,nombre,descripcion?,modalidad,sedeId?,precioBase,duracionMin?}`.                                                                                                                    |
| `GET /api/aliados/:allyId/servicios/:serviceId`         | Consulta el detalle persistido del aliado.                                                                                                                                                                             |
| `GET /api/servicios/:serviceId`                         | Detalle público activo/publicado; excluye servicios vinculados a sedes desactivadas.                                                                                                                                   |

## Datos simulados para probar

1. Configura `AUTH_SIMULATED=true` en `.env`, arranca `pnpm --filter @veto/api dev` y crea un aliado con `POST /api/aliados`.
2. Usa el `data.aliado.id` devuelto como `x-dev-ally-id` en Thunder Client. Es una identidad simulada, no prueba credenciales ni permisos reales.
3. Para HU-015 el aliado debe ser `CLINICA`; crea una sede y usa su `id` como `sedeId` al guardar un servicio `EN_SEDE`.
4. `VET_INDEPENDIENTE` y `CLINICA` pueden crear servicios; `TIENDA` no. Un servicio `A_DOMICILIO` puede dejar `sedeId` vacío o asociarse opcionalmente a una sede activa.

La contraseña se almacena con `scrypt`. El correo se normaliza a minúsculas y la unicidad la aplica `citext UNIQUE`; la base valida además el celular de diez dígitos.

## Estado de dependencias y alcance

Antes de estos cambios, `IdentidadModule`, `AliadosModule` y `ServiciosModule` eran módulos vacíos; no existían registro API, operaciones de sede ni gestión de servicios. La migración implementa esos servicios base.

El middleware real de sesión/JWT, inicio de sesión y emisión/validación de credenciales **siguen sin estar implementados**. La guarda `DevelopmentAllyGuard` es solo de desarrollo; reemplázala por la autenticación real antes de desplegar. También siguen fuera de alcance gestión de veterinarios HU-012..014, especies atendidas HU-021, horarios HU-016/022 y búsqueda HU-024..028.

## Límite del esquema compartido

`servicio.sede_id` representa la ubicación en sede y puede opcionalmente señalar la sede asociada a un servicio a domicilio. El esquema no tiene campo de texto para zona/cobertura de atención domiciliaria. No se añadió una columna fuera del modelo compartido; si la historia requiere esa cobertura, coordinar una migración con el equipo.
